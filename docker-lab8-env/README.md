# Docker lab 8 — Один образ, два окружения

Сквозная рабочая нумерация: 8. Оригинал: ЛР4 «Environment Variables & Configuration» из `Docker_Volumes_EnvVars.pdf`, страницы 23–28; исходное приложение на страницах 16–18. Flask/Python 3.11 и PostgreSQL 15 сохранены для совместимости с заданием.

В проекте один runtime image. Development и production-like контейнеры получают разные env-файлы, отдельные PostgreSQL, сети и volumes. В обеих сетях имя БД `db`; localhost не используется для поиска соседнего контейнера. API отвечает на `/` и `/db-test`.

## Запуск и проверка

Нужны Docker Engine/Desktop, Python 3 на хосте и POSIX shell (на Windows — WSL или другая подходящая среда).

```bash
chmod +x configure-env.sh run.sh
./run.sh start
./run.sh check
./run.sh status
./run.sh stop
```

При первом запуске `start` сам вызывает конфигурацию, если файлов ещё нет. Существующие локальные env-файлы сохраняются; отдельный вызов `configure-env.sh` перед каждым запуском не нужен. Этот скрипт можно вызвать вручную только при первоначальной подготовке: он создаёт `.env.development`, `.env.production` и служебные PostgreSQL env-файлы в `.local/`. Пароли и SECRET_KEY генерируются независимо, файлы имеют режим 0600; значения не печатаются. Повторное configure не перезаписывает их без явного `--force`. Для обычной повторной проверки генерировать новые значения не надо. Смена пароля env не меняет пароль роли уже инициализированной БД.

Реальные env-файлы и `.local/` нельзя коммитить; в целевом репозитории их исключают через `.git/info/exclude`. Файл `.gitignore` здесь специально не создаётся. `.env.example` безопасен и хранится в Git. `.dockerignore` исключает реальные env-файлы из build context.

По умолчанию Docker выбирает свободные порты на 127.0.0.1 и `start` показывает URL без секретов. Для фиксированных портов нового запуска:

```bash
./run.sh start --run-id my-run --port-dev 5052 --port-prod 5053
```

Каждый run имеет префикс `devops-lab8-RUN_ID-*` и labels owner/lab/run. Порты БД не публикуются. Start существующего сохранённого запуска без `--run-id` возобновляет его после stop. Чтобы применить другой образ или новую конфигурацию, создай отдельный новый run ID; restart существующего контейнера не меняет его окружение.

До сборки, записи конфигурации и создания Docker-ресурсов проверяются все запланированные имена контейнеров, сетей и volumes без фильтра по labels. Любое занятое имя блокирует новый запуск, включая объект без наших labels. Возобновление требует совпадения owner/lab/run у всех восьми сохранённых ресурсов; проверяется весь набор до первого `docker start`. Перед подключением volume его labels дополнительно проверяются после создания.

При новом запуске сначала действительно выполняется `docker build --target test` с 12 unit-тестами. Они проверяют Boolean-разбор, missing variables, диапазон порта, запрет DEBUG в production, отсутствие секретов в ответах и закрытие DB-соединения. Затем строится runtime stage без tests. `check` дополнительно делает реальные HTTP/SQL-проверки обоих режимов, сравнивает image IDs, доказывает разделение данных и запускает отдельные отрицательные контейнеры с плохим окружением.

Результаты: `REPORT.md`, `evidence/verification.json`, `evidence/build-tests.txt`, `evidence/build-runtime.txt`. В evidence нет реальных паролей и ключей. После ручной работы останови контейнеры командой `./run.sh stop`; named volumes останутся.

## Очистка

```bash
./run.sh cleanup
```

Удаляет только контейнеры и сети текущего run, оставляет volumes. Для отдельного осознанного удаления данных:

```bash
./run.sh cleanup --delete-data
```

Для предыдущего run можно добавить `--run-id ПРЕЖНИЙ_ID`. Глобальные prune и удаление чужих ресурсов не используются. Env-файлы и evidence не удаляются автоматически.

## Границы учебного результата

Production-like означает другой набор настроек и DEBUG=false. В целях воспроизведения задания сервер запускается через `python app.py`; это Flask development server, а не готовый публичный production deployment. Внешних публикаций нет. `python-dotenv` оставлен среди зависимостей источника, но загружать файлы в приложении не требуется: `--env-file` передаёт окружение через Docker.

Для штатной остановки этого учебного сервера Dockerfile задаёт `STOPSIGNAL SIGINT`: Python/Flask обрабатывает его без ожидания принудительного SIGKILL. Это учитывает особенности главного процесса контейнера PID 1.
